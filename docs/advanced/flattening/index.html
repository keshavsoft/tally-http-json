Deep dive: flattening nested voucher data

A step-by-step explanation of the parent voucher, nested entries, TDL traversal, and flat output.

Documentation home / Advanced

The goal

We want one row per ledger entry, while retaining the voucher date and number so that each row remains traceable to its parent voucher.

Step 1 — start with the business shape

A Receipt voucher contains header-level values and a collection of ledger entries. The header values belong to the voucher; each entry has its own ledger name, amount, and flags.

Voucher 471
  Date: 20261017
  AllLedgerEntries:
    - LedgerName: Cash
      Amount: 100.00
    - LedgerName: Customer A
      Amount: -100.00

Step 2 — express the relationship in JSON

The following is a simplified teaching example, not a verbatim Tally response:

[
  {
    "Date": "20261017",
    "VoucherNumber": "471",
    "AllLedgerEntries": [
      {"LedgerName": "Cash", "Amount": "100.00"},
      {"LedgerName": "Customer A", "Amount": "-100.00"}
    ]
  }
]

Step 3 — what does flatten mean here?

Instead of one voucher object containing an array, produce one output object per entry. Copy the parent voucher's date and number into every child row, then retain the child fields.

[
  {
    "ParentVoucherNumber": "471",
    "ParentVoucherDate": "20261017",
    "LedgerName": "Cash",
    "Amount": "100.00"
  },
  {
    "ParentVoucherNumber": "471",
    "ParentVoucherDate": "20261017",
    "LedgerName": "Customer A",
    "Amount": "-100.00"
  }
]
This output is illustrative and simplified. Tally's JSONEx response may wrap fields with type and value, and may include additional metadata.

Step 4 — identify the collection traversal

In the tested TDL definition:

  • Source Collection points to the Receipt-voucher source.
  • Walk: AllLedgerEntries traverses the child ledger-entry collection.
  • Source Fetch: Date,VoucherNumber makes the source voucher values available during traversal.
  • Fetch requests child methods such as LedgerName, Amount, and IsDeemedPositive.
  • Compute defines the parent-number and parent-date methods on the resulting rows.

Step 5 — check the actual response

The observed result included parentvouchernumber and parentvoucherdate. For the screenshot's example, the values were 471 and 20261017. This was the confirmation that the parent context could be exposed alongside each ledger-entry row in the tested setup.

Step 6 — why the parent values must be repeated

After flattening, the original parent-child nesting is no longer the primary structure. Repeating the parent's identifying values on each row preserves traceability. Without them, an entry such as Cash / 100.00 could be hard to associate with its source voucher.

Step 7 — understand the row count

Flattening is one row per child entry, not one row per voucher. A voucher with two ledger entries produces two rows. A voucher with several entries produces several rows. This can make the flattened output larger than a header-only voucher list, even though the structure is easier to analyze.

Step 8 — where JavaScript can help

A JavaScript utility can perform a similar transformation on already-returned JSON. It could accept data, a path to the nested array, and a definition of which parent fields to retain. The exact contract should be designed before implementation.

Core takeaway: flattening changes the shape of the data, not the underlying business relationship. Parent values travel with each child so the relationship remains understandable.
